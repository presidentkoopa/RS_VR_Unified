// RS_VR_Unified -- one AddEventHandlers list.
//
// The six source packages each shipped their own GameInfo block. Separately
// that worked because AddEventHandlers APPENDS across pk3s rather than
// replacing. Merged, they collapse into the single list below -- 15 handlers,
// which is the whole VR interaction stack running every tic.
//
// ORDER IS LOAD-BEARING AND CURRENTLY UNDECLARED.
//
// Not one of the five packages declares an Order on any handler. With no Order,
// GZDoom falls back to registration sequence -- which means the list below IS
// the ordering, and it was previously an accident of pk3 load order rather than
// a decision. That is fine only for as long as no two handlers write the same
// field in the same tic, and three of them do: RS_Held, RS_HolsterManager and
// RR_Reload all write GripClaim*, and the reader acts on ANY value rather than
// on its own (see RS_Holsters.zs:1019). Fixing that properly means either
// giving the claim fields per-owner identity, or declaring Order explicitly
// here. Until then, do not reorder this list casually -- it is the tiebreak.
//
// Sequence rationale, foundation-first:
//   1  RS_HandsAlwaysOn ... RS_GrabViz   hands publish pose/basis and resolve
//                                        their own grab before anyone reads it
//   2  RS_HolsterManager, StartLoadout   torso anchors + spawn loadout
//                                        with the holster manager)
//   4  RR_Reload                         consumes hands' basis AND the pouch,
//                                        so it must see both already updated
//   5  wr_Rig                            the wrist rig. Claims no grip, but it
//                                        is NOT a read-only handler: see below.
//
// WHY wr_Rig GOES LAST, AND WHY "LAST" MEANS TWO OPPOSITE THINGS.
//
// It writes. wr_Rig::equipInstantly assigns player.ReadyWeapon,
// player.OffhandWeapon, player.PendingWeapon = WP_NOCHANGE, and
// bOffhandWeapon on both the weapon and its SisterWeapon, then calls
// SetPsprite. The wheel's own code says so where it reads those fields back:
// "Read BEFORE the first equip: equipInstantly rewrites both". So this is a
// SECOND writer of ReadyWeapon/OffhandWeapon, alongside RS_HolsterManager.
//
// It is still safe last, but for a specific reason rather than by being
// harmless: it writes only in response to a committed card -- a netevent --
// and never from WorldTick. Groups 1-5 run their WorldTick ahead of it, so
// they observe the change on the FOLLOWING tic, never a half-applied one.
//
// AND THE TRAP: this list is NOT one ordering, it is two opposite ones.
//   WorldTick and NetworkProcess run FRONT TO BACK  (first registered first).
//   InputProcess and UiProcess run BACK TO FRONT    -- EventManager::Responder
//     in src/events.cpp walks `handler = LastEventHandler; handler; handler =
//     handler->prev`.
// wr_Rig overrides InputProcess and returns true to swallow +attack /
// +altattack / +use while the ring is open. Being LAST therefore makes it the
// FIRST handler offered every input event, which is exactly what the wheel
// needs -- but it is the opposite of what "last" means three lines above.
//
// Nothing else here overrides InputProcess today, so this is currently moot.
// The day any RS_* handler does -- a grab or holster gesture on a bound key --
// it will be registered AHEAD of wr_Rig and therefore polled AFTER it, and the
// wheel will eat the key first whenever a card is hovered. Read this note
// before concluding the new handler is broken.
//
// ONE OF THE WHEEL'S THREE HANDLERS, DELIBERATELY.
//
// RS_WeaponWheel/mapinfo.txt registers only wr_Rig and says at length that
// this is a decision rather than an oversight: wr_GunTag (wr_gunhud.zs, the
// on-gun ammo readout) is switched off because the readout does not work, and
// an earlier audit that recommended registering both unregistered handlers had
// read the file headers rather than the implementations. That decision is
// carried across verbatim, not re-litigated during a merge.
//
// THE PRICE IS PAID BY THE THIRD ONE, wr_StatEvents (wr_stattracker.zs), and
// it is worth separating because the wheel's own note does not. wr_StatEvents
// is the ONLY writer of the wr_StatLedger inventory item; wr_StatTracker's
// static readers -- called from the ring's data sheet (zscript.zs) and from
// wr_stats.zs -- are the only readers. Unregistered, the ledger is never
// created, every reader's "have data" flag returns false, and the kills /
// shots / accuracy / headshot rows hide themselves. In-headset that reads as
// a data card with fewer rows than expected, which is why it has survived.
// REGISTERED 2026-08-30, on the owner's call. The stat rows were asked for
// explicitly, and four defects in the tracker itself (audit #31 pellets, #32
// per-hand attribution, #33 the MAG row's ammo pools, #34 the headshot
// percentage) were fixed the same day -- all of it dead code while the one
// writer of the ledger never ran. wr_GunTag stays off; see above.
GameInfo

}
